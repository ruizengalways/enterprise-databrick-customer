# Framework Certification Model

Certification is evidence, not a label.

A green unit-test suite proves only what it executed. This repository therefore separates certification into levels so documentation cannot accidentally claim more than the evidence supports.

## Levels

| Level | Name | Required evidence |
|---|---|---|
| C0 | Contract | customer metadata loads and validates against the exact framework SHA |
| C1 | Deterministic semantics | source fixtures and expected business outcomes pass deterministic tests |
| C2 | Package integration | customer tests import/use the built framework package without copying framework source |
| C3 | Databricks runtime | real Databricks execution produces expected Bronze/Silver outcomes for the scenario |
| C4 | Recovery & failure | duplicate/out-of-order/late/bad-schema/bad-data/checkpoint/replay scenarios are detected, contained, repaired and reconciled |
| C5 | Release certification | C0-C4 evidence is tied to exact framework/customer SHAs, environment/runtime metadata and a retained certification artifact |

`certification/matrix.yml` is the machine-readable status source.

## Rules

1. **Exact SHA required.** Every certification run records the resolved 40-character framework commit.
2. **No false green.** Missing Databricks credentials must not be converted into a successful runtime certification. It is `not_run`/`blocked`, not `passed`.
3. **Expected outcomes are independent.** Expected business results live in this customer repo, not generated by the framework code under test.
4. **No copied framework source.** The customer installs the framework as a package/dependency.
5. **Platform-independent and platform-dependent evidence are separate.** C0-C2 can run on GitHub-hosted runners; C3-C5 require a real Databricks environment.
6. **Runtime certification is pattern-specific.** P10 passing does not certify P02, and a metadata-only P14 declaration does not certify P14 runtime behavior.
7. **Recovery is part of correctness.** For production claims, happy-path output alone is insufficient.

## Required runtime assertions

Each pattern must define assertions appropriate to its semantics. Examples:

- full snapshot: row/key counts and exact current-state equality;
- watermark/lookback: retry idempotency, overlap deduplication, high-watermark correctness and soft-delete state;
- CDC: source position, duplicate/redelivery handling, operation counts, delete propagation and ordering;
- SCD2: at most one current row per key, no overlapping ranges and correct history transitions;
- events: event identity deduplication, ordering/watermark behavior and canonical event count;
- snapshot diff: snapshot ordering, insert/update/delete derivation and interval-fidelity caveat.

## Failure injection catalogue

Full certification should deliberately exercise at least:

- duplicate delivery
- out-of-order CDC
- late event
- delete event / snapshot absence
- null business key
- quarantinable bad value
- additive schema change
- incompatible schema change
- partial downstream failure
- reconciliation mismatch
- replay/backfill
- checkpoint reset/recovery where streaming state exists
- bad code release vs bad data recovery distinction

The expected lifecycle is **Detect -> Contain -> Alert/Evidence -> Repair -> Reconcile -> Resume**.

## Evidence artifact

Local CI generates `certification-evidence.json` and uploads it as a workflow artifact. Runtime certification must later extend the same evidence with workspace/runtime, deployed bundle/job/pipeline identifiers, source cutoffs, reconciliation results and recovery-test results.
